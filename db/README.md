# db/

資料庫相關的 SQL。全部都是拿去 Supabase 主控台的 **SQL Editor** 貼上執行,不是給程式跑的。

| 檔案 | 用途 | 會不會改到資料 |
|---|---|---|
| `introspect.sql` | 讀出正式環境現在真正的結構,用來核對 `../supabase-schema.sql` 有沒有過期 | 否,純唯讀 |
| `metrics.sql` | 使用狀況查詢:多少社團、多少真的在用、代打成效等 | 否,純唯讀 |
| `migrations/001_add_updated_at.sql` | 加上「最後修改時間」欄位與觸發器 | 會,但只新增欄位,不刪不覆寫 |

## 建議順序

1. 先跑 `introspect.sql`,確認 `../supabase-schema.sql` 的內容跟正式環境一致。
   目前該檔案裡 `subs` 與 `photography` 兩張表的欄位是**從程式碼反推的,尚未核對過**,
   對完之後請把差異修正回去。
2. 跑 `metrics.sql` 看現況。標著【估計】的段落數字不精確,原因見下。
3. 想要「留存率」這類指標,再跑 `migrations/001_add_updated_at.sql`,
   之後 `metrics.sql` 的 4b 段就能用。

## 為什麼有些數字只能是估計

**`events` 和 `clubs` 沒有連在一起。** `events.host`(主辦單位)是使用者自己打字填的自由文字,
表單範例就是「薇閣 × 明德」這種一場活動兩個社團的寫法。資料庫裡沒有任何欄位明確指向
「這場活動屬於哪個社團」,所以只能拿社團名字去 host 字串裡找,兩種錯都會發生:

- **低估**:社團登記全名「明德熱音社」,活動 host 只寫「明德」→ 對不上
- **誤判**:社團名字很短很通用 → 誤中不相干的活動

看這些數字之前,先跑 `metrics.sql` 的 2b 段看看 host 實際長什麼樣,再判斷可信度。

要根治的話得加一欄 `events.club_id` 指向 `clubs.id`,並在發布活動的表單改成從既有社團中選,
但這會動到 `src/App.jsx` 的活動表單,而且舊資料仍需人工比對回填 —— 屬於另一件事,尚未進行。

## 為什麼「有沒有回來編輯過」現在問不出來

所有表都只有 `created_at`(建立時間),沒有記錄「後來被改過」。
所以「登記完就再也沒動」和「持續在維護」的社團,在資料上長得一模一樣。

`migrations/001_add_updated_at.sql` 補上這個欄位,但**只對執行之後的編輯有效** ——
過去誰改過什麼沒有留下痕跡,補不回來。越早跑,累積的資料越多。
