# db/

資料庫相關的 SQL。全部都是拿去 Supabase 主控台的 **SQL Editor** 貼上執行,不是給程式跑的。

| 檔案 | 用途 | 回傳量 | 會不會改到資料 |
|---|---|---|---|
| `verify-schema.sql` | 核對 `../supabase-schema.sql` 與正式環境是否一致,**只列出不一致的地方** | **一格** | 否,純唯讀 |
| `snapshot.sql` | 現況快照:帳號、留存、內容量、活動、代打全部濃縮 | **一格** | 否,純唯讀 |
| `introspect.sql` | 完整結構 dump(欄位、外鍵、RLS)。`verify-schema.sql` 報出問題時才需要 | 四張大表 | 否,純唯讀 |
| `metrics.sql` | 逐項明細:社團名單、host 長相、每週趨勢、比對診斷 | 十五張表 | 否,純唯讀 |
| `migrations/20260804_add_updated_at.sql` | 為 clubs / venues / events / subs 加上「最後修改時間」欄位與觸發器 | — | 會,但只新增欄位,不刪不覆寫 |
| `health-check.sql` | 找出會讓統計失真的髒資料(孤兒認領碼、無主無碼、同名社團等) | **一格** | 否,純唯讀 |
| `dm-claim-list.sql` | 二次宣傳用:未認領社團/活動的 DM 名單,每則已代入認領碼 | **一格** | 否,純唯讀 |
| `dm-school-gap.sql` | 二次宣傳用:雙北尚未加入名錄的高中(陌生開發名單) | **一格** | 否,純唯讀 |

## 建議順序

**日常只要跑前兩個就夠了。**

1. **`verify-schema.sql`** — 確認文件跟正式環境還對得上。
   看到「完全一致」就過關;有列出東西再去跑 `introspect.sql` 拿完整結構。

   2026-08-06 已核對過一次:`subs`、`photography` 完全正確,`venues.tags` 實為
   `venues.contact`,已修正。之後每次改結構後重跑即可。

2. **`health-check.sql`** — 先確認數字是乾淨的,再去看數字。

   2026-08-08 靠它發現 `edit_keys` 有 16 筆認領碼指向已被刪除的 clubs/events,
   讓「未認領筆數」從實際的 21 虛報成 37,差了將近一倍。單看某張表的
   `count(*)` 看不出這種問題,要交叉比對才會現形。孤兒碼已清除,
   還原檔留在 `backup/20260808_orphan_edit_keys.sql`。

3. **`snapshot.sql`** — 一次拿到所有關鍵數字。不必先跑 migration,
   跟 `updated_at` 有關的那列會自動顯示「尚未啟用」。

這兩份都刻意設計成**只回傳一格**:點那一格、Ctrl+C、貼回來就好,
不必框選表格。SQL Editor 的表格結果複製起來容易漏欄或跑版。

4. 想深入看某一項(哪些社團、host 到底怎麼寫的、每週趨勢)再跑 `metrics.sql`。

5. 想要「有沒有回來維護內容」這個指標,跑 `migrations/20260804_add_updated_at.sql`。
   跑完之後 `verify-schema.sql` 會多報四列 `updated_at`「實際有,文件沒寫」,
   那是正常的,不是問題。

   注意「建檔逾 10 分鐘後被改過」這個判準:建完馬上修錯字不算,
   隔一段時間回來調整才算。這是刻意的——要量的是「有沒有回頭維護」,
   不是「有沒有打錯字」。

## 為什麼有些數字只能是估計

**`events` 和 `clubs` 沒有連在一起。** `events.host`(主辦單位)是使用者自己打字填的自由文字,
表單範例就是「薇閣 × 明德」這種一場活動兩個社團的寫法。資料庫裡沒有任何欄位明確指向
「這場活動屬於哪個社團」,所以只能拿社團名字去 host 字串裡找,兩種錯都會發生:

- **低估**:社團登記全名「明德熱音社」,活動 host 只寫「明德」→ 對不上
- **誤判**:社團名字很短很通用 → 誤中不相干的活動

看這些數字之前,先跑 `metrics.sql` 的 2b 段看看 host 實際長什麼樣,再判斷可信度。

要根治的話得加一欄 `events.club_id` 指向 `clubs.id`,並在發布活動的表單改成從既有社團中選,
但這會動到 `src/App.jsx` 的活動表單,而且舊資料仍需人工比對回填 —— 屬於另一件事,尚未進行。

實際跑過的例子(用假資料驗證,`metrics.sql` 第 10b 段就是在查這個):

| 社團 | 比對到的活動主辦欄 | 實際上 |
|---|---|---|
| 明德熱音社 | 明德熱音社 | 正確 |
| 薇閣熱音社 | (比對不到) | ❌ 漏算,它辦了 host =「薇閣 × 明德」那場 |
| 熱音 | 明德熱音社 | ❌ 誤算,它一場都沒辦,只是名字兩字被包含在裡面 |

同一份資料同時犯了兩種相反的錯。所以看 `pct_active` 之前,一定先跑 10b 和 10c 用肉眼掃過。

要根治的話得加一欄 `events.club_id` 指向 `clubs.id`,並把發布活動的表單改成從既有社團中選,
但這會動到 `src/App.jsx` 的活動表單,而且舊資料仍需人工比對回填 —— 屬於另一件事,尚未進行。

## 兩種「留存」是不同的問題

| 想問的事 | 資料來源 | 現在問得出來嗎 |
|---|---|---|
| 有沒有再回來**登入** | `auth.users.last_sign_in_at` | ✅ 現成的,`metrics.sql` 第 2 段 |
| 有沒有再回來**維護內容** | 需要 `updated_at` 欄位 | ⚠️ 要先跑 20260804 migration |

**登入那邊有個重要的低估問題。** App 用的是 supabase-js 預設設定(`src/supabase.js` 沒有傳任何 options,
所以 `persistSession` 和 `autoRefreshToken` 都是開的)。同一台裝置回訪時,token 是背景自動續期,
**不會產生新的登入事件**,`last_sign_in_at` 就不會更新。結果是:一個天天在用但從來沒登出過的人,
在數字上看起來像三個月沒出現過。所以第 2、3 段的活躍數字是**地板值**,真實活躍只會更高。

另外第 2 段的幾個數字**加起來不會等於總數**,這不是算錯:
- 註冊了但從沒完成登入的人,`last_sign_in_at` 是 NULL,不會落入任何活躍/沉睡分類(已另外列為 `never_signed_in`)
- `active_30d` 本來就包含 `active_7d`,是包含關係不是互斥,不能相加

## 為什麼「有沒有回來編輯過」要另外加欄位

所有表都只有 `created_at`(建立時間),沒有記錄「後來被改過」。
所以「登記完就再也沒動」和「持續在維護」的社團,在資料上長得一模一樣。

`migrations/20260804_add_updated_at.sql` 補上這個欄位,但**只對執行之後的編輯有效** ——
過去誰改過什麼沒有留下痕跡,補不回來。越早跑,累積的資料越多。

跑之前先知道三件事(都已在本地 Postgres 16 用同結構空庫實測確認):

1. **App 的編輯是真正的 UPDATE。** `src/App.jsx:254-260` 走的是
   `supabase.from(table).update()`,不是刪掉再新增,所以 trigger 會正常觸發。
2. **`claim_item()` 認領舊資料會被記成一次編輯。** 它內部是
   `update clubs set user_id = auth.uid()`,同樣觸發 trigger。認領是一次性的
   帳號綁定,不是內容維護,會讓 `pct_edited` 偏高。用 `metrics.sql` 第 14 段
   看還有多少舊資料未認領,判斷灌水程度。
3. **`subs` 有系統寫入。** `api/remind-subs.js` 寄完提醒信會更新
   `reminder_sent_at`,那不是使用者編輯。`metrics.sql` 第 15 段有扣掉的版本。
